## Context

MLBlock is structured as a polyglot monorepo containing a FastAPI backend (`backend/`) and a React 19 / TanStack Start frontend (`frontend/`). The application is currently deployed on Render as separate services defined in `render.yaml`. 

The deployment target is a self-hosted VPS (`oracle-arm`, Oracle Cloud Ampere A1 ARM64 architecture, configured in `~/.ssh/config` at IP `141.253.110.210`, user `ubuntu`) managed by Coolify. Coolify acts as a self-hosted PaaS with Docker Compose and Traefik reverse proxy integration. External dependencies remain external: PostgreSQL is hosted on Supabase (accessed via pooler on port 6543), authentication uses Supabase Auth, and GPU jobs are orchestrated remotely on Vast.ai via REST.

## Goals / Non-Goals

**Goals:**
- Provide reproducible containerization for both backend (Python 3.11 + `uv`) and frontend (Node 20 build + Nginx static server) compatible with ARM64 (`linux/arm64`).
- Orchestrate backend and frontend services via a production `docker-compose.coolify.yml` file suitable for direct import into Coolify.
- Provide automated redeployment triggered on push to `main` branch, integrated with GitHub Actions to ensure redeployment occurs after CI verification passes.
- Provide a clear, actionable guide in `docs/coolify-deployment.md` for configuring the VPS host, setting up Coolify, mapping domain/Traefik routing, configuring secrets, and establishing webhooks.

**Non-Goals:**
- Self-hosting the PostgreSQL database or Supabase Auth service on the VPS (Supabase managed services remain authoritative).
- Running GPU compute workloads directly on the Oracle ARM VPS (Vast.ai remains the GPU execution provider).
- Modifying backend API contracts, database schemas, or frontend canvas logic.

## Decisions

### Decision 1: Single Docker Compose Stack (`docker-compose.coolify.yml`) vs Multiple Coolify Applications
- **Choice**: Deploy as a unified Docker Compose stack in Coolify using `docker-compose.coolify.yml`.
- **Rationale**: A unified Compose file couples frontend and backend releases to the exact same Git commit, simplifies inter-service networking, allows shared healthcheck policies, and makes environment variable management cohesive in Coolify's UI.
- **Alternatives Considered**: Creating two separate Coolify applications in the UI. Rejected because it requires dual webhook management, separate repository tracking, and complicates local DNS and CORS alignment.

### Decision 2: Backend Containerization with `uv` and Python 3.11 Slim
- **Choice**: Use a multi-stage Docker build starting from `ghcr.io/astral-sh/uv:python3.11-bookworm-slim` (or copying the `uv` binary into `python:3.11-slim-bookworm`).
- **Rationale**: `uv` provides native ARM64 support, fast dependency resolution, and is the project's canonical package manager. The repository's `requirements.txt` is known to be stale and unmaintained, making `uv sync` from `pyproject.toml` and `uv.lock` essential.
- **Alternatives Considered**: Using standard `pip install -r requirements.txt`. Rejected because `requirements.txt` lacks critical dependencies like `torch` and `torchvision` and contains obsolete packages.

### Decision 3: Frontend Containerization via Multi-Stage Node 20 + Nginx Alpine
- **Choice**: Multi-stage build with `node:20-alpine` for asset compilation (`npm ci && npm run build`) followed by `nginx:alpine` serving the generated `dist/client` static assets.
- **Rationale**: Production frontend assets are purely static HTML/JS/CSS generated by Vite and TanStack Start SSG. Nginx provides low memory overhead (~15MB RAM on ARM64), fast static asset serving with gzip/brotli compression, and reliable fallback routing (`try_files $uri $uri/ /index.html`) for client-side SPA routing.
- **Alternatives Considered**: Running a Node.js SSR runtime container. Rejected because the production frontend build outputs static client bundles, and running Node in production would waste memory on the VPS.

### Decision 4: Frontend API URL Build-Time Injection
- **Choice**: Pass `VITE_API_BASE_URL`, `VITE_SUPABASE_URL`, and `VITE_SUPABASE_PUBLISHABLE_KEY` as Docker build arguments (`ARG`) and environment variables during the build stage in `frontend/Dockerfile`.
- **Rationale**: Vite statically inlines `import.meta.env.VITE_*` variables at compile time. Defining them as `ARG` in Docker allows Coolify to supply the public backend domain and Supabase parameters during image generation.
- **Alternatives Considered**: Runtime environment variable replacement via entrypoint shell scripts. Rejected because it introduces complexity and risks breaking hashed bundle assets.

### Decision 5: CI/CD Continuous Redeployment via Post-CI GitHub Actions Workflow
- **Choice**: Add `.github/workflows/deploy-coolify.yml` that triggers Coolify's deployment webhook using `curl` after the primary CI pipeline (`.github/workflows/ci.yml`) succeeds on `main`.
- **Rationale**: Coolify provides a deploy webhook (`GET /api/v1/deploy?uuid=...` with Bearer auth). Triggering this webhook from GitHub Actions guarantees that bad commits that fail backend tests or frontend linting never trigger a production rebuild on the VPS.
- **Alternatives Considered**: Direct GitHub push webhook configured in Coolify. While viable and documented as an option, direct push triggers deployments even if tests fail in GitHub Actions. The GitHub Actions approach provides a safer, gated pipeline. Both options will be documented.

### Decision 6: ARM64 / Ampere A1 Host Considerations
- **Choice**: Ensure all base images (`python:3.11-slim-bookworm`, `node:20-alpine`, `nginx:alpine`) are official multi-platform images with first-class `linux/arm64` support.
- **Rationale**: The Oracle Cloud instance `oracle-arm` runs Ampere Altra ARM64 cores. Utilizing official multi-arch images ensures no emulation overhead or QEMU compatibility issues.

## Risks / Trade-offs

- **[Risk] High memory usage during PyTorch / package installation on ARM64** → **Mitigation**: Use pre-compiled Python wheels from PyPI/PyTorch index; configure swap memory (e.g. 4GB swapfile) on the `oracle-arm` instance prior to running builds; utilize Docker build layer caching.
- **[Risk] Frontend build failure due to missing placeholder Supabase env vars** → **Mitigation**: Set fallback dummy default build args in `frontend/Dockerfile` matching CI configuration (`https://placeholder.supabase.co`) so builds succeed even before production secrets are fully populated.
- **[Risk] Coolify webhook URL / token exposure** → **Mitigation**: Store `COOLIFY_WEBHOOK_URL` and `COOLIFY_API_TOKEN` as GitHub Repository Secrets, never hardcoding them in workflow YAML or public files.
- **[Risk] Database connectivity timeouts via Supabase pooler** → **Mitigation**: Ensure `DATABASE_URL` uses port `6543` with transaction pooling mode, and ensure special characters in passwords remain percent-encoded.

## Deployment & Setup Plan

1. **Host Preparation (`oracle-arm`)**:
   - Verify Docker Engine and Docker Compose plugin are active on `oracle-arm` (`docker --version`, `docker compose version`).
   - If not yet installed, install Coolify via official command (`curl -fsSL https://cdn.coollabs.io/coolify/install.sh | sudo bash`).
   - Ensure firewall/security list on Oracle Cloud allows ingress on ports 80, 443 (web traffic) and 8000 (Coolify dashboard).
2. **Coolify Project Setup**:
   - Add new Project and Environment in Coolify dashboard.
   - Connect Git repository (MLBlock) with branch set to `main`.
   - Select "Docker Compose" build pack and specify `docker-compose.coolify.yml`.
   - Populate environment variables for backend and frontend.
3. **Continuous Deployment Setup**:
   - Copy the application deployment webhook URL and Bearer token from Coolify.
   - Add `COOLIFY_WEBHOOK_URL` and `COOLIFY_API_TOKEN` to GitHub repository secrets.
   - Commit and push changes to `main` to trigger the automated build and deployment.
